# AGENTS.md — toxicwind Codex

This project documents `github.com/toxicwind`'s 200\+ repository estate as a granular deep-wiki, Gwern-adjacent in tone. It is not a marketing site. Every page carries dense analytical value; introductory filler, hedging, and pleasantries are actively removed on sight.

## About this documentation site

- Built on Mintlify (MDX \+ `docs.json`).
- Two tabs: **Documentation** (four architectural sections) and **Repository Codex** (per-repo pages) plus a **Swarm Ops** group for the operational plane.
- Use the Mintlify MCP server, `https://mcp.mintlify.com`, to edit content and settings via MCP.
- Use the Mintlify docs MCP server, `https://www.mintlify.com/docs/mcp`, to query information about using Mintlify via MCP.

## Voice and stance

- Second person ("you"), active voice.
- Sentence case for headings.
- Assume the reader is a systems-level principal engineer. Skip primers. Cite AST nodes, capability flags, timing budgets, and observed failure modes; skip the "what is Python" step.
- Cynical without becoming ranty. Every dismissal names the specific mechanism it is dismissing.
- Never invent internals. If a claim is not grounded in a workspace file, the sandbox, a `web_fetch`, or the user's own words, drop it or mark it as an assumption.
- Never use em dashes (—) or en dashes (–) as punctuation in prose. Rewrite the sentence, split it, or use a comma, colon, or parentheses. Verbatim ports and code blocks keep their original characters.

## Component conventions

- Use `<Steps>` for sequential incantations, `<CodeGroup>` for polyglot examples, `<Accordion>` for failure taxonomies, `<Card>` / `<CardGroup>` for navigation surfaces (never raw HTML), `<Note>` / `<Warning>` / `<Tip>` for callouts.
- Code blocks always carry a language tag and, when useful, a title (`bash Step 3`, `json mcp/servers.json`, `python swarm_maximal.py`).
- Cross-reference other pages at the bottom of every doc with root-relative Markdown links.

## MCP \+ CDN awareness

This site was generated by a Mintlify agent operating under network constraints. Two facts colour every operational instruction it emits:

1. **The editor `bash` has no network.** No `curl`, `wget`, `pip`, `npm`, `node`, `python`. All research is done via `web_fetch`, `web_search`, or `sandbox_bash` against a separately cloned tree. Documentation that shows install commands is describing what the **reader** should do on their own machine.
2. **The estate is CDN-fallback-aware.** `sovereign_helper.pip_with_fallback()` cycles through `pypi.org` → aliyun → tsinghua. Documentation must preserve this pattern. Never rewrite it to a single-mirror form.

## Content boundaries

- Public-surface repositories only. If `toxicwind/some-repo` is not visible on GitHub without authentication, treat it as out of scope.
- Do not document credentials, cookies, or PATs given in user messages. Warn the user to rotate and continue with placeholders.
- The `neo-osint` repository is an OSINT dossier on a consumer product (BAT glo hyper Fukuoka Strawberry). Treat as a stylometric artifact of the estate; document the shape, not the target.

## Writing budget

- Every page 3000\+ characters.
- Every section leads with a concrete claim, then evidence, then implication.
- Prefer tables to bullet lists when comparing three or more items.
- If a page cross-references another, it links to it. No dangling "see the swarm docs".

## Do not

- Do not run `bash` writes against page content (`sed -i`, `echo >`). Use `edit`/`write`.
- Do not shorten `.env` values in prose to look tidy; preserve their exact shape, including known defects (leading-space `LENS_API_KEY=`, etc.).
- Do not invent CI stages. If a workflow file is not in the source tree, the pipeline described does not exist.
