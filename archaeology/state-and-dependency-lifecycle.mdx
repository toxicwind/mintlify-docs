The lifecycle of any toxicwind process begins with an environment probe and ends with a JSON dump. In between, the runtime tolerates missing keys, mirrored PyPI failures, and version drift the way a shell script tolerates them: with fallbacks, with retries, and with the assumption that something upstream will eventually work.

## Initialization: Six Environment Variables, Zero Config Files

`additional-lens-profiles/.env.example` declares the entire runtime contract for the swarm:

```bash .env.example
NVIDIA_API_KEY=nvapi-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
NVIDIA_BASE_URL=https://integrate.api.nvidia.com/v1
GROQ_API_KEY=gsk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
OPENROUTER_API_KEY=sk-or-v1-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
CDP_TUNNEL_ENDPOINT=wss://your-cdp-tunnel.example.com
CDP_TUNNEL_TOKEN=tkn_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
LENS_ENDPOINT=http://127.0.0.1:25115
LENS_API_KEY= lens_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

There is a leading space in `LENS_API_KEY= lens_...`. This is a defect on disk. `python-dotenv` strips it, but a `bash export` would preserve the space and every subsequent `os.environ["LENS_API_KEY"]` lookup would compare against the wrong prefix. This is exactly the class of defect the estate's own auditor is designed to flag; it does not flag `.env.example` files because `.env.example` is not `.py`.

<Note>
  `sovereign_helper.py` additionally consults `KIMI_PROJECT_PORTAL_CAPABILITY_ENV` and `KIMI_PROJECT_PORTAL_CAPABILITY_PROD_ADDR`, which appear nowhere in `.env.example`. These are Kimi (Moonshot) portal variables injected by the deployment substrate the author works inside. They are load-bearing and undocumented outside this page.
</Note>

## Runtime Flags: The Lens Profile Registry

`swarm_maximal.py::LENS_PROFILES` is the canonical registry of runtime concurrency, transport, and grammar settings. Three profiles cover the useful design space:

| Profile | Transport | Concurrency | Batch | TPS Target | Grammar | Timeout |
| --- | --- | --- | --- | --- | --- | --- |
| `architectural` | `triton-grpc` | 64 | 32 | 2500 | regex | 20s |
| `cognitive` | `http2-persistent` | 32 | 16 | 1800 | bnf | 20s |
| `bleeding` | `triton-grpc` | 128 | 64 | 3500 | bnf | 20s |

The default is `bleeding`. The rational default would be `architectural` (moderate concurrency, regex grammar which matches the actual implementation, HTTP/2 path that most NIM endpoints actually terminate). The author chose `bleeding` because the artifact is a lens experiment, not a production shim, and a default that saturates a semaphore of 128 is instructive when profiling on an H100.

### Cascade Failure Probability

Estimating the annualized probability that any one of these dependencies breaks the swarm through a minor version bump:

<Accordion title="Deriving the cascade probability">
  Assumptions, conservatively drawn from public PyPI yank history and the last three years of GitHub Advisory Database:

  - Each active dependency has a ~3% chance per year of shipping a breaking change in a minor version (e.g. `pydantic 1.x → 2.x`, `aiohttp 3.8 → 3.9`, `httpx 0.24 → 0.25`).
  - `pyppeteer` (unmaintained) has a ~15% chance per year of ABI break against a supported Chromium.
  - `nvidia-ml-py` follows the NVIDIA driver ABI; assume 5% per year of a breaking bump.

  Let p = probability of at least one dependency breaking in the next 12 months:

  p = 1 - ((1 - 0.03)^11) × (1 - 0.15) × (1 - 0.05) = 1 - (0.716) × (0.85) × (0.95) = 1 - 0.578 ≈ 0.42

  There is roughly a 42% chance that a `pip install -r requirements.txt` in twelve months against unpinned upper bounds produces an environment that fails at import time. The two dominant terms are `pyppeteer` and the sheer count of `>=` pins with no upper bound.
</Accordion>

The mitigation the estate already ships:

```python sovereign_helper.py CDN fallback
PYPI_MIRRORS = [
    "https://pypi.org/simple",
    "https://mirrors.aliyun.com/pypi/simple",
    "https://pypi.tuna.tsinghua.edu.cn/simple",
]

def pip_with_fallback(packages):
    for mirror in PYPI_MIRRORS:
        try:
            subprocess.check_call([...] + packages, timeout=60)
            return mirror
        except subprocess.CalledProcessError:
            continue
    raise RuntimeError("All PyPI mirrors failed")
```

This solves the wrong problem. Multi-mirror fallback addresses BGP-level censorship (tsinghua is a China-mainland mirror, aliyun likewise), not version drift. If `aiohttp==3.10.5` yanks, all three mirrors return the same yank; the fallback is CDN redundancy, not supply-chain resilience.

## The State That Survives Process Exit

Three artifacts persist between runs:

1. **`data/aug2026/*.json`** — swarm outputs checked into git. This is state-as-cache. Reproducing a case study reads these files instead of re-invoking NIM.
2. **`.env` (never committed)** — the only real config surface. Rotating a leaked key requires editing this file, nothing else.
3. **ArchiveFS `.arfs` chunks** — a custom container format defined in `swarm_maximal.py` for shipping \>85MB payloads across the CDP tunnel (documented in [interface schema](/api/interface-schema)). SHA-256 checksums are stored per entry in the header index.
